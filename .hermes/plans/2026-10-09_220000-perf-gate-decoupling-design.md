## 1. 契約定義（先定名，再設計；避免「零回歸」被偷換語意）

| 契約 | 定義 | **不是**什麼 |
|---|---|---|
| **C1 封版契約** | INC-282 A 案 Task 1+2 封版 commit `2d1b9ed2` 的內容與範圍仍可被驗證（只動 4 檔、tree 可解析、計算層可重現 7/8/9 月 net） | 不是「該 commit 與現在的工作區逐位元相同」 |
| **C2 本輪範圍契約** | 被審對象（＝發布候選）的變更檔案集 ⊆ 本次核准範圍，且核准範圍與獨立 CIO 核准紀錄一致 | 不是「檔案數少就通過」 |
| **C3 環境健康度** | 現行各閘門的紅燈狀態，與**受治理的基準快照**相比是否新增 | **不是** Task1+2 零回歸；不併入 C1/C2 的結論 |
| **C4 發布一致性** | 核准來源版本、實際建置來源、產物內容雜湊、實際推送內容四者一致 | 不是「驗收 PASS 即授權發布」；也不等於「Git tree 相同」 |

> **明文禁止的重新定義**：不得把「零回歸」寫成「整個 repo 沒有任何歷史紅燈」，
> 也不得簡化成「只要本輪檔案乾淨就通過」。

## 2. 架構：把現行單一耦合檢查拆成 4 個獨立斷言

```
F1｜封版契約      輸入 = 常數 BASELINE_SHA(2d1b9ed2)              時間相依：無
F2｜本輪範圍      輸入 = 候選版本 + ALLOWED_FILES + CIO 核准紀錄   時間相依：無
F3｜環境健康度    輸入 = 現行閘門輸出 + 受治理基準快照             時間相依：有（明示）
F4｜發布一致性    輸入 = 核准來源／建置來源／產物雜湊／推送內容     時間相依：無
```

**四者輸出分立**，各自 PASS/FAIL、各自 detail；總結區分兩欄：

```
【任務契約】（發布必要條件）F1 PASS ／ F2 PASS ／ F4 PASS
【環境健康度】（獨立呈現）    F3 FAIL（新增 3 條，見清單）→ 依 Q4 裁定是否影響發布
```

→ 一方紅燈**不得**冒充另一方的結果（今日症狀：F3 的紅燈讓 F1/F2 看起來像壞了）。

### 2.1 F1｜封版契約
- `BASELINE_SHA = 2d1b9ed2…`（**固定歷史基準，保留其歷史比較用途，不得因它讓測試失敗就移除**）
- 斷言：可解析、stat 僅含 4 檔、AST 可解析、`performance_core` 重現 7/8/9 月 net。
- 輸入改為常數後，與「被審對象」完全脫鉤 → **不再受 f63acd6b 之類的當日 commit 影響**。

### 2.2 F2｜本輪範圍契約（**補強：必須檢查工作樹，不只檢查 commit**）

現行閘門**根本沒有**驗「本輪變更是否只有核准範圍」。本次要補的核心能力，
且**必須四層盤點**（已知存在 27 檔 dirty）：

| 層 | 對象 | 判準 |
|---|---|---|
| ① | **候選 commit 的變更範圍** | 變更集 ⊆ `ALLOWED_FILES`，**且** `ALLOWED_FILES` 與獨立 CIO 核准紀錄一致（Q1） |
| ② | **候選 commit 之後的未提交變更**（工作樹） | 必須**證明不會被納入本輪交付** |
| ③ | **未追蹤檔案** | 同上 |
| ④ | **發布產物及其依賴檔案** | 交付清單須明示列出（含 `snapshot`／`db`／校正檔等依賴），且與實際產物一致 |

- **不要求清理 27 檔**；要求的是**證明它們不會被意外納入本輪交付**。
  作法（二擇一或併用）：`交付清單 ∩ (② ∪ ③) = ∅`；或沿用 2026-10-08 定案的 `produced ∈ after − before` 差集證明。
- **FAIL-CLOSED**：`ALLOWED_FILES` 未提供／為空／無法解析，或第 ②③④ 層無法判定 → FAIL。
- **allowed set 不由被審對象自我宣告**；呼叫端亦不得自行擴張（Q1）。
- 只驗 commit 變更集而忽略工作樹 → 可能出現「commit 範圍完全乾淨、實際發布內容卻混入其他變更」。本層即為防此。

### 2.3 F3｜環境健康度（時間相依，獨立呈現；**補強：快照治理**）

**白名單 → 受治理基準快照**：新增 `gate_baseline_dividend_caliber.json`：

```json
{"as_of":"2026-10-09","expires_at":"2026-11-08","created_by":"...","approval_ref":"...",
 "reason":"...", "content_sha256":"...",
 "fail_set":["<既有 4 條>"], "released_20261005":["Pending schema 五欄齊備","status 非 ENUM"]}
```

**快照治理規則（實作前必須納入）**

| # | 規則 | 目的 |
|---|---|---|
| **R-a** | 快照**只能記錄經核實的既有狀態**；**不得自動吸收本次新增 FAIL**——新增者必須經人工裁定為既有，並留下理由與證據 | 防止快照成為新的白名單漏洞 |
| **R-b** | 每次更新必須提供**前後差異、納入與移除的項目、理由及核准紀錄** | 可追溯 |
| **R-c** | **產生該次 FAIL 的同一流程不得自行核准快照更新**（職責分離） | 防自我核准 |
| **R-d** | 保留**不可覆寫**的歷史版本（append-only 或版本目錄），能追溯每次快照變動 | 可回溯 |
| **R-e** | **2026-10-05 已釋放的兩條規則不得藉更新快照重新吸收**（＝R2） | 防回吞 |
| **R-f** | 「本次更新 N 條」**只提供可見性，不足以阻止消音**；真正的保護必須來自**獨立核准與可追溯的差異紀錄** | 明示可見性 ≠ 防護 |

**判定**：
1. 現行 FAIL 集合 ⊆ 快照 → 既有紅燈**不**造成 F3 FAIL（正確辨識歷史問題）。
2. 集合差（快照外）非空 → **F3 FAIL 並指名每條新紅燈與其來源檢查**。
3. 快照缺失／損毀／來源不可驗證／**超過 `expires_at`** → **FAIL-CLOSED**（Q2）。
4. `content_sha256` 與內容不符 → FAIL-CLOSED（防事後改寫）。

**不再用 `startswith("變更範圍")` 濾除**：改為**分類呈現**——
`變更範圍` 類標記為 `環境/範圍類` 並**完整列出檔案、異動類型與歸屬**，
讓未提交工作樹的影響可見（今日第 8 條即被此法遮蔽）。若涉及核准範圍以外的**實際異動**，
依 Q3 由 **F2 阻擋**，不得只列警示就繼續發布。

### 2.4 F4｜發布一致性（**補強：比對實際發布對象**）

tree hash 相符是**必要條件**，但**不充分**。F4 至少核對四項：

| # | 核對對象 | 不一致時 |
|---|---|---|
| ① | **CIO 核准的 source tree／commit** | 阻擋 |
| ② | **實際建置使用的來源版本** | 阻擋（防核准後換來源重產） |
| ③ | **產物清單及各產物的內容雜湊** | 阻擋 |
| ④ | **實際推送的發布內容**是否與核准清單一致 | 阻擋 |

> **對靜態網站而言，Git tree 相同不必然代表部署後的每個 HTML／JSON 檔都與核准版本相同。**
> 因此第 ③④ 項必須以**內容雜湊**核對，而非只比 tree。

目前 `cio_approve.py` 已綁 tree hash；本項＝把該綁定擴充為「來源＋產物＋推送內容」的一致性輸出。
